## 目的

  バッファが消す前に**読み取り専用で**アーカイブし、後段で集計・公開する。
- プロジェクトの価値（オーナー、2026-09-03）:
  **有機的で面白い見える化を通して、ユニークで有用な動きを抽出し、拡散する。**
- README にある後段の構想: behavioral scatter、replay、DID の relationship
  constellation。これは構想であり、設計は **未決**。

## 制約

- **読み取り専用**、GET のみ。600 reads/min の read budget（README 記載）を大きく下回る運用。
- **礼儀 > 完全性**。export は 1 回試行、失敗は次サイクル。
- サーバ事実（2026-09-02/03 実測、要再検証）:
  - `since` は後方ページングしない。200 件上限は新しい側から適用。
  - `/export` がリング全体（JSONL、連番連続）を返す唯一の完全ソース。
  - リングは 10 MiB（`room_ring_bytes`=10,485,760。CHANGELOG 0.11.3 は「5 MiB」と書いており未解決）のバイト上限。**保持仕様は 09-02（0.11.3）に変更**されており、
    09-02 の寿命 1–3 時間は旧ロジック下の数字。09-03〜07 の実測（1–99% トリム、raw の export から）:
    kibble 17–207 分、technocore 28–186 分、inference-agents 3.7–43 時間、credence 5.5–9.5 日。
    忙しい 2 室は 17–20 時 JST を中心に（喪失の約 17% は他の時間帯）1 間隔内に半減することがある。
    export 間隔は min(今回, 前回) の寿命×0.5 と head レート推定の小さい方、下限 600 秒、
    上限 3600 秒。寿命が ~13 分を下回ると下限に当たり喪失が再開する（記録はされる）。
  - 全ルーム合計の byte budget（5 GiB、09-07 で 13.7%）に達すると per-room floor は 32 KiB。
    その時は現方式では追随不能（上限側の破綻シナリオ、監視のみ）。
  - `since` の非後方ページングは上流 issue #481 でも再現済み。503 は 0.12.1（09-05）以降激減。
  - メッセージに reply フィールドは無い。
- 運用基盤は家庭内 PC の tmux 1 セッション。冗長化は無い（**未決**: 必要かどうか）。
- Python stdlib のみ、単一ファイル。
- 公開する数字は「少なくとも」。ギャップ記録は削除しない。

## 成功条件

- **Stage 1（測定可能）**
  - 24 時間連続で、全ルームに各自の `export_interval`（+1 サイクル）以内の `export:` ログがある
  - その間の `coverage_gaps` 新規行が export 時刻のものだけ
  - `parse_failures` に新規行が無い
- **公開用の数字**: 同じ境界で SQL と Python の独立導出が一致し、別セッションでも
  再現でき、`coverage_gaps` の記録範囲に重複が無いこと（あれば併合済み）を
  クエリで検証している（ルール 7）
- **Stage 2 / 拡散**: 何を「ユニークで有用な動き」とするか、どこへ・どの頻度で
  拡散するかは **未決**。決まるまで成功条件は書かない。
