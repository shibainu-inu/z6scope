# Findings 2026-09-03 — カバレッジの実態と過去データの価値

スナップショット: `data/z6scope.sqlite3` @ **2026-09-03 07:26 UTC**（16:26 JST）。
すべての数字は下の SQL でそのまま再導出できる（ルール 7）。個別 DID は書かない
（ルール 6）。公開時の数値は「少なくとも」で読むこと（ルール 5）。

## 1. 発端: `since` は前方ページングではない

2026-09-02 の健全性チェックで、collector が毎サイクル「coverage gap … evicted
before read」を記録していた。検証の結果:

- リングは連番連続（export 実測: 23,279 → 26,570 → 30,442 → 14,423 件。
  ~10 MiB のバイト上限なので件数は本文長で変動する）。
- read-only GET で `since=<最新−5000>` を要求すると、`first_seq` は
  **最新−185** だった。200 件上限は **新しい側** から適用され、`since` 以降の
  古い 200 件は返らない。
- したがって旧 collector が「evicted」と記録した範囲の大半は、その時点では
  サーバ上に存在していた（飛ばしただけ）。`/export` は使われていなかった
  （発動条件 `last_seq − cursor` が常に 0 のデッドコード）。

対処（コミット済み）: 1 時間ごとの `/export` を各ルームで実行し、`coverage_gaps`
は **export 時点でリングより古く、かつ手元に無い範囲 = 恒久喪失** だけを記録する。

### 2.1 時系列は「収集器のカバレッジ」を描いてしまう

technocore の時間別件数は 13k/h・12k/h・11k/h の山と ~2k/h の谷を示すが、
山は **export ウィンドウそのもの**、谷はポーリングのみ（真値の ~17%）。
現時点のデータで時間別ボリュームを描くと、ルームの活動ではなく collector の
状態を描くことになる。**時系列系の可視化は完全連続ウィンドウに限定する**か、
修正後（2026-09-03 以降）のデータを使う。

```sql
SELECT strftime('%m-%d %H', ts) h, COUNT(*) FROM messages WHERE room='technocore' GROUP BY 1 ORDER BY 1;
```

### 2.2 恒久喪失

例: technocore 3,371,859–3,414,618（約 42k 件、09-02 夜間 JST）はリングから
落ちてから export したため回収不能。`coverage_gaps` に記録済み。

### 2.3 `coverage_gaps` の二つの体制（削除はしない）

- **2026-09-03 07:2x UTC まで（旧体制）**: ポーリングが飛ばした範囲を毎サイクル
  記録。後の export で埋まった分も含むため **過大**で、範囲は重複している。
  公開数値には使わず、必ず「実際に無い seq」で再計算する。
- **以降（新体制）**: export 時にリングより古く手元に無い範囲のみ。
  `meta.last_export_max:{room}` が走査済みの上限。

旧体制のレコードを実態に照合する SQL（記録範囲のうち本当に無い件数）:

```sql
WITH g AS (SELECT room, gap_start, gap_end FROM coverage_gaps)
SELECT g.room, SUM(g.gap_end-g.gap_start+1) recorded,
       SUM(g.gap_end-g.gap_start+1) - SUM((SELECT COUNT(*) FROM messages m
            WHERE m.room=g.room AND m.seq BETWEEN g.gap_start AND g.gap_end)) still_missing_upper_bound
FROM g GROUP BY g.room;   -- 重複範囲があるため upper bound
```

## 3. 内容の構造（集計のみ）

### 3.1 サーバのメッセージに reply フィールドは無い

フィールドは `seq, ts, from, text, nonce, sig` のみ（poll / export とも、raw で確認）。
`messages.reply_to` は本文の正規表現由来で、現状すべて NULL。
**返信・相互性の可視化は本文からの推定でしか作れない**（設計課題）。

### 3.2 ルームごとの性格

| room | DID 数 | 1 回きり DID | ≥100 件の DID | 上位 10 DID の占有 | 本文ユニーク率 | 平均字数 | ≥10 回反復本文の占める割合 |
|---|---:|---:|---:|---:|---:|---:|---:|
| credence | 564 | 338 | 2 | 33.7% | 0.833 | 394.5 | 3.0% |
| inference-agents | 1,764 | 571 | 4 | 21.5% | 0.804 | 115.9 | 18.7% |
| kibble | 1,451 | 272 | 61 | 57.0% | 0.757 | 266.2 | 4.0% |
| technocore | 45,747 | 24,599 | 11 | 7.3% | 0.355 | 78.2 | **63.2%** |

- credence / inference-agents: 長文・高ユニーク・**完全観測**。価値が確定している。
- kibble: 少数の常連（≥100 件が 61 DID、上位 10 で 57%）による長文の場。
- technocore: 極端に広く浅い。反復本文が 63%。

```sql
WITH per AS (SELECT room, did, COUNT(*) c FROM messages GROUP BY room, did)
SELECT room, COUNT(*) dids, SUM(c=1), SUM(c>=100),
  ROUND(100.0*(SELECT SUM(c) FROM (SELECT c FROM per p2 WHERE p2.room=per.room ORDER BY c DESC LIMIT 10))/SUM(c),1)
FROM per GROUP BY room;
SELECT room, ROUND(1.0*COUNT(DISTINCT body_hash)/COUNT(*),3), ROUND(AVG(body_len),1) FROM messages GROUP BY room;
WITH b AS (SELECT room, body_hash, COUNT(*) c FROM messages GROUP BY room, body_hash)
SELECT room, ROUND(100.0*SUM(CASE WHEN c>=10 THEN c END)/SUM(c),1) FROM b GROUP BY room;
```

### 3.3 technocore は二層構造

- ≥100 回出現する本文は 34 種。上位 7 本文（42–57 字）は **それぞれ ~8,500 の
  異なる DID** が 1.34 回ずつ投稿している — 少数のスパムではなく、大量の
  一回性アイデンティティによる同一テンプレのエコー。
- DID の内訳: テンプレ本文のみ **21,979** / テンプレを一度も投稿しない
  **23,364** / 両方 **404**。
- 「有機的な動き」を探す対象は後者 23,364 DID 側の本文。テンプレ側は
  「伝播の速度・波形」として集計する対象。

```sql
WITH tpl AS (SELECT body_hash FROM messages WHERE room='technocore' GROUP BY body_hash HAVING COUNT(*)>=100),
per AS (SELECT did, SUM(body_hash IN tpl) t, SUM(body_hash NOT IN tpl) nt FROM messages WHERE room='technocore' GROUP BY did)
SELECT (SELECT COUNT(*) FROM tpl), SUM(nt=0), SUM(t=0), SUM(t>0 AND nt>0) FROM per;
WITH b AS (SELECT body_hash, COUNT(*) c, COUNT(DISTINCT did) d FROM messages WHERE room='technocore' GROUP BY body_hash ORDER BY c DESC LIMIT 8)
SELECT c, d, ROUND(1.0*c/d,2) FROM b;
```

### 3.4 ルーム間の橋渡し

複数ルームに現れる DID: **209**（2 室 190、3 室 18、4 室 1）。全 49,297 DID の 0.4%。

## 4. 結論

**確定している価値**
- credence と inference-agents の（ほぼ）完全アーカイブ。
- technocore 4 本・kibble 3 本の完全連続ウィンドウ（合計 ~13 万件）。ここは
  「少なくとも」抜きで語れる。

**限定的な価値**
- ポーリングのみ時間帯の technocore / kibble。5–7 分おきに最新 200 件を
  取った系統サンプルとしては使えるが、量・時系列・DID 数には使えない。

**プロジェクト価値（可視化 → ユニークで有用な動きの抽出 → 拡散）への含意**
- 候補となる集計指標: テンプレ vs 非テンプレの比率とその推移、テンプレの伝播
  波形、新規 DID の流入率、ルーム間橋渡し数、ルームごとの本文長・ユニーク率。
- reply が無いため、相互性・会話構造は本文ベースの推定設計が必要。
- 修正後の collector で 1 時間ごとの完全ウィンドウが連続するので、時系列は
  2026-09-03 以降のデータで作るのが最も誠実。

**書いていないこと**: 個別 DID の分類、ボット判定、推定値の事実化。
